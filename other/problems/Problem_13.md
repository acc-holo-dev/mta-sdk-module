# Problem 13 — release-пайплайн вызывает CLI с позиционным пресетом, который парсер cli.py не принимает: публикация Release недостижима

**Задача:** `other/tasks/Task_25.md` — Definition of Done V2 — итоговая проверка соответствия проекта
**Вердикт:** Проект не соответствует задаче (статическая проверка, 2026-09-02)
**Серьёзность:** P1 — значимое требование задачи (публикация GitHub Release после успешного build/test pipeline) фактически не выполняется, поскольку все job'ы релизной матрицы падают из-за несовпадения синтаксиса вызова CLI, однако требования безопасности и корректности SDK при этом не нарушены.

## Суть проблемы
Проект статически соответствует почти всем условиям Definition of Done: архитектурные каталоги разделены, developer workflow (mta init/new function/build/test) работает без правок registry/CMake, binder обнаруживает count/type/optional/variadic/callback с понятными ошибками, lifecycle построен на поколениях ресурса, worker-потоки не вызывают Lua, userdata имеет стабильную идентичность, example.md покрывает все конструкции, mta doctor реально проверяет окружение, а интеграционный harness поднимает контролируемый pinned-сервер (логи подтверждают пройденный прогон). Единственное несоответствие — release-пайплайн: .github/workflows/release.yml вызывает CLI с позиционным именем пресета, которое текущий парсер cli.py не принимает, поэтому шаги Build/Test/Package завершаются ошибкой argparse и публикация Release недостижима в текущем виде.

## Несоответствия

### 1. GitHub Release публикует только &lt;module&gt;.dll/.so после успешного build/test pipeline
- **Статус:** PARTIAL
- **Требуется:** публикация только модульных бинарников после успешного build/test pipeline.
- **Фактически:** структура пайплайна корректна (Build → Test → Package → Publish, files: dist/*, а cmd_package кладёт в dist/ ровно один бинарник модуля), но все три шага матрицы передают пресет позиционным аргументом, который парсер cli.py отклоняет: «build linux-gcc» → unrecognized arguments (exit 2), «test win-mingw all» → invalid choice для suite, «package linux-gcc» → unrecognized arguments. Каждый job матрицы (linux-gcc, win-mingw, win-msvc) падает на шаге Build, softprops/action-gh-release никогда не выполняется, поэтому «после успешного build/test pipeline» релиз не публикуется вовсе; имя публикуемого файла также &lt;module&gt;-&lt;version&gt;-&lt;platform&gt;-x64.dll, а не буквально &lt;module&gt;.dll.
- **Доказательство:** .github/workflows/release.yml:67 «python other/tools/mta/cli.py build ${{ matrix.preset }}», :70 «cli.py test ${{ matrix.preset }} all», :84 «cli.py package ${{ matrix.preset }}» против other/tools/mta/cli.py:613-615 (build — только --preset), :618-620 (test — позиционный suite с choices [all, unit, lua, integration]), :631-633 (package — только --preset); cli.py:573 — артефакт называется «{name}-{version}-{platform}-x64{suffix}».

- Developer workflow: mta init (cli.py cmd_init копирует checkout-шаблон и переписывает config/module.toml), mta new function (cmd_new — один .cpp с MTA_FUNCTION), mta build (cmake --preset), mta test (ctest) — без ручного редактирования registry/CMake

- Lifecycle: Hub увеличивает generation при остановке ресурса (resources.cpp:77-90); на ResourceStopped инвалидируются callbacks (callback.cpp:217-230 + повторная проверка generation в call:166-173), отменяются queued-задачи и таймеры (scheduler.cpp:445-486), Store очищается; completion/таймер устаревшего поколения отбрасываются в pump() до доступа к Lua (scheduler.cpp:248-353); регрессия покрыта other/tests/lua/scripts/072_restart.lua и реальным restart-сценарием интеграции

- Userdata: стабильная идентичность через MTA_OBJECT — метатаблица «mta.&lt;module&gt;.&lt;имя&gt;» (userdata.hpp:195-210, 285-287); typeid(T).name() используется только как warning-fallback для необъявленных типов, не как public identity (api.md:405-408)
- Documentation: other/documents/example.md позволяет самостоятельно создать function (§2), async function (§3), timer (§4), callback (§3), object (§5), state (§6) и error handling (mta::lua::raise_error в §3/§4, обработка error в completion, примеры сообщений об ошибках в §2/§5)

- Release (объём артефактов): публикуются только бинарники модуля — release.yml uses files: dist/*, а cmd_package кладёт в dist/ единственный файл &lt;module&gt;-&lt;version&gt;-&lt;platform&gt;-x64.dll/.so; публикация структурно стоит после шагов Build и Test

## Рекомендации по устранению
1. Исправить вызов build в .github/workflows/release.yml:67 — передавать пресет флагом, а не позиционно: `python other/tools/mta/cli.py build --preset ${{ matrix.preset }}`, поскольку парсер build принимает только --preset (cli.py:613-615); сейчас позиционная форма даёт «unrecognized arguments» (exit 2).
2. Исправить вызов test в release.yml:70 — suite должен быть единственным позиционным аргументом (choices [all, unit, lua, integration], cli.py:618-620), поэтому пресет передавать флагом --preset: `python other/tools/mta/cli.py test --preset ${{ matrix.preset }} all`; если подкоманда test ещё не поддерживает --preset, добавить её в парсер по аналогии с build/package, иначе позиционное имя пресета снова даст «invalid choice» для suite.
3. Исправить вызов package в release.yml:84 — передавать пресет флагом: `python other/tools/mta/cli.py package --preset ${{ matrix.preset }}`, поскольку парсер package принимает только --preset (cli.py:631-633).
4. Перед пушем прогнать все три команды локально для пресетов матрицы (linux-gcc, win-mingw, win-msvc) и убедиться, что argparse больше не возвращает exit 2 ни на одном шаге Build/Test/Package.
5. Проверить пайплайн end-to-end: после исправления синтаксиса все три job'а матрицы должны проходить шаги Build → Test → Package успешно, чтобы структурно следующий за ними шаг публикации (softprops/action-gh-release, files: dist/*) реально выполнялся — в текущем виде он недостижим, так как каждый job падает на шаге Build.
6. Сверить имя публикуемого артефакта с буквальным требованием «только &lt;module&gt;.dll/.so»: сейчас cmd_package кладёт в dist/ файл &lt;module&gt;-&lt;version&gt;-&lt;platform&gt;-x64.dll/.so (cli.py:573); если требуется имя ровно &lt;module&gt;.dll/.so — привести именование артефакта в cli.py к требованию (объём публикации при этом корректен: ровно один модульный бинарник).
