# Problem 8 — Неполное покрытие сценариев раздела 32 реальными integration-тестами (12 из 19)

**Задача:** `other/tasks/Task_18.md` — Интеграционное тестирование с реальным MTA server
**Вердикт:** Проект не соответствует задаче (статическая проверка, 2026-09-02)
**Серьёзность:** P1 — значимые нереализованные требования: 7 из 19 обязательных сценариев раздела 32 не имеют реальных тестов, а объявленный каталог test suite пуст, хотя ключевая инфраструктура реального сервера и регрессионный тест раздела 33 реализованы.

## Суть проблемы
Инфраструктура реального MTA server реализована полноценно: `other/server/` с полным harness, пиннинг конкретной nightly-сборки 24140, все пять CLI-команд `mta server`, 13 шагов harness, изоляция от глобальной установки, binaries вне Git и автоматический regression-тест раздела 33 на restart ресурса (два INTEGRATION_RESULT: PASS плюс отсутствие STALE_TASK_DELIVERED и SHOULD_NEVER_FIRE). Единственное несоответствие — покрытие сценариев раздела 32: реализованы 12 из 19 (встроенный MAIN_LUA в `other/server/mta_server.py`), отсутствуют реальные тесты для module unload, resource start/stop как отдельных сценариев, multiple resources, userdata invalidation, old callback after restart и multiple timers after restart. Каталог `other/tests/integration/` пуст (только README.md), хотя объявлен местом test suite. Побочное наблюдение вне требований задачи: CI (ci.yml строка 160) вызывает `mta server test`, который argparse CLI не принимает, поэтому canary через эту команду фактически не запускает integration.

## Несоответствия

### 1. Существуют реальные integration-тесты минимум для всех 19 сценариев раздела 32
- **Статус:** PARTIAL
- **Требуется:** для минимум всех 19 сценариев раздела 32 должны существовать реальные integration-тесты, выполняемые на реальном MTA server.
- **Фактически:** покрыты 12 из 19 сценариев (включая resource restart, old async task after restart через STALE_TASK_DELIVERED и shutdown with active workers через SHOULD_NEVER_FIRE). Нет реальных тестов для: module unload; resource start и resource stop как отдельных сценариев (только неявно: автостарт ресурса и stop внутри restart); multiple resources (создаётся единственный ресурс sdkintegration, mta_server.py строки 390–395); userdata invalidation (есть лишь проверка типов аргумента «userdata validation», а не инвалидация объектов между поколениями); old callback after restart (отдельный колбэк, пережидающий рестарт, не вооружается — проверяется только старый async task); multiple timers after restart (в генерации 1 один таймер 50 мс, завершающийся до рестарта; в генерации 2 один setTimer). Каталог `other/tests/integration/` пуст (только README.md), хотя other/server/README.md строка 21 заявляет «The integration test suite lives in other/tests/integration/».
- **Доказательство:** other/server/mta_server.py строки 272–354 (MAIN_LUA): единственные check() — module load, function registration, return values, argument validation, userdata, userdata validation, async task valid, timer, callback, async completion; лог реального прогона other/server/logs/20260902-052043/server.log строки 19–25, 33–35 подтверждает тот же набор; `git ls-files other/tests/integration` → только README.md.

- Integration harness выполняет все 13 шагов раздела 31: сборка модуля, временный серверный каталог (tempfile.mkdtemp + copytree, строки 374–377), установка модуля в x64/modules (385–388), тестовый ресурс meta.xml+main.lua (390–395), конфигурация mtaserver.conf с module/resource (400–414), запуск сервера (run_server, 432–465), ожидание готовности через поллинг консольного вывода (wait_for_results, 595–642; преждевременный выход сервера = ошибка), вызов Lua integration-тестов (MAIN_LUA), сбор stdout/stderr/log в other/server/logs/<ts>/server.log (419–426), проверка ожидаемого вывода (два INTEGRATION_RESULT: PASS, отсутствие STALE_TASK_DELIVERED и SHOULD_NEVER_FIRE, 608–633), корректная остановка (stop_process: graceful console exit → kill, 662–690), возврат exit code, очистка временных файлов (rmtree в finally, 427–428).
