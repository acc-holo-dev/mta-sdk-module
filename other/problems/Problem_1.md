# Problem 1 — Отсутствует MTA_STATE/mta::state, а developer code в source/functions/ напрямую использует Registry, Scheduler и ABI-слой

**Задача:** `other/tasks/Task_6.md` — Public API, internal API и архитектурные границы
**Вердикт:** Проект не соответствует задаче (статическая проверка, 2026-09-02)
**Серьёзность:** P1 — значимые нереализованные требования: два пункта чек-листа выполнены лишь частично (отсутствуют явно названные MTA_STATE/mta::state и нарушен запрет на использование Registry/Scheduler/ABI glue в source/functions/), при этом критические требования безопасности/корректности не нарушены.

## Суть проблемы
Фасад `<mta/sdk.hpp>` реализован и является основным include для всех файлов `source/functions/`; направление зависимостей functions → library → sdk → MTA соблюдено, Registry/Runtime/Bind соответствуют своим границам (без бизнес-логики, без знания фич, без http/crypto), внутренние слои сохранены. Найдено два частичных несоответствия: в чек-листе явно названные `MTA_STATE` и `mta::state` отсутствуют во всей кодовой базе, а developer code в `source/functions/` напрямую использует Registry (`functions_list.cpp`), Scheduler (`timers.cpp`) и ABI-слой `mta::module` (`version.cpp`), что противоречит пункту чек-листа об их неиспользовании. Отсутствие `mta::Player`/`mta::Vehicle` — осознанное, документированное решение (`native/resource.hpp`) и нарушением не считается.

## Несоответствия

### 1. Umbrella header экспортирует наиболее важные public APIs: MTA_FUNCTION, MTA_OBJECT, MTA_STATE и mta::*
- **Статус:** PARTIAL
- **Требуется:** Umbrella header должен экспортировать наиболее важные public APIs, в том числе явно названные в чек-листе задачи макрос `MTA_STATE` и API `mta::state`. Отсутствие `mta::Player`/`mta::Vehicle` нарушением не считается: в §43 это примеры (список открыт — «...»), PROMT.md §17 делает native-типы условными («только если соответствующий MTA API доступен»), а `source/sdk/native/resource.hpp:5-13` документированно обосновывает, что замороженный ABI модуля не даёт player/vehicle API.
- **Фактически:** `source/mta/sdk.hpp` подключает `sdk/registry/registry.hpp` (`MTA_FUNCTION`) и `sdk/objects/userdata.hpp` (`MTA_OBJECT`), а также экспортирует `mta::lua::args/push_results`, `mta::async` (Callback/Task/run/Scheduler), `mta::timer::after/every`, `mta::log`, `mta::events::trigger`, `mta::resources::{Hub,Store}`, `mta::userdata::Registry`+`MTA_METHOD`, `mta::Resource`. Однако макрос `MTA_STATE` и какой-либо API `mta::state` отсутствуют во всей кодовой базе.
- **Доказательство:** grep `MTA_STATE` и `mta::state` по всему `source/` даёт 0 совпадений; при этом `MTA_FUNCTION` экспортирован через `sdk/registry/registry.hpp` (строка 105 `source/mta/sdk.hpp`), `MTA_OBJECT` — через `sdk/objects/userdata.hpp` (строка 285).

### 2. Developer code не подключает внутренние headers напрямую — Registry/Scheduler/Lua stack helpers/ABI glue не используются в source/functions/
- **Статус:** PARTIAL
- **Требуется:** Developer code не должен подключать внутренние headers напрямую; Registry, Scheduler, Lua stack helpers и ABI glue не должны использоваться в `source/functions/`.
- **Фактически:** Первая часть соблюдена — во всех 20 `.cpp` файлах `source/functions/` единственные проектные include — `<mta/sdk.hpp>` и `<library/base/handle_map.hpp>` (плюс MTA-заголовок `ILuaModuleManager10.h` в `version.cpp`). Но вторая часть нарушена: developer code напрямую обращается к синглтонам Registry и Scheduler и к функциям ABI-слоя `mta::module`. Смягчающий контекст: фасад сам документирует `mta::async::Scheduler` как экспортируемый API (`sdk.hpp:24`), для таймеров есть предназначенный developer'у путь `mta::timer::after/every` (`timer_demo.cpp`), а Lua stack helpers в functions не используются (`stack_dump.cpp` использует raw `lua_*` C API — задокументированный escape hatch для body-style макросов).
- **Доказательство:** `source/functions/info/functions_list.cpp:11,24` — `mta::registry::Registry::instance().functions()`; `source/functions/async/timers.cpp:19,35` — `mta::async::Scheduler::instance().post_timer()`/`cancel_timer()`; `source/functions/info/version.cpp:12-13` — `mta::module::info()`/`manager()` из ABI-слоя `source/sdk/abi/module.hpp` (в списке экспорта фасада не задокументирован).

## Что уже соответствует
- Umbrella header `source/mta/sdk.hpp` существует и включается как `#include <mta/sdk.hpp>`; include-корень `source/` задан как PUBLIC в `CMakeLists.txt:169-174`
- Фасад экспортирует `MTA_FUNCTION`, `MTA_OBJECT`, `MTA_METHOD` и `mta::lua::args/push_results/raise_error`, `mta::async` (Callback/Task/run/Scheduler), `mta::timer::after/every`, `mta::log`, `mta::events::trigger`, `mta::resources::{Hub,Store}`, `mta::userdata::Registry`, `mta::Resource`
- `#include <mta/sdk.hpp>` — основной include во всех 20 `.cpp` файлах `source/functions/`
- Прямых include внутренних headers (`registry.hpp`, `scheduler.hpp`, `stack.hpp`, `abi/*`) в `source/functions/` нет
- Направление зависимостей functions → library → sdk → MTA соблюдено: functions используют sdk (фасад) и `library/base/handle_map.hpp`; library/base не зависит ни от sdk, ни от functions; sdk идёт к MTA через `other/third_party/mta-sdk` и `mta_lua`
- Зависимость SDK от functions отсутствует: включений headers functions в `source/sdk` и `source/library` нет (grep — 0 совпадений)
- Registry не содержит бизнес-логики: `source/sdk/registry/registry.cpp` — только хранилище Spec, `register_all` → `manager.RegisterFunction` и мост от биндера
- Runtime не знает деталей фич: `source/sdk/runtime` (scheduler, callback, timer, task) полностью обобщённый (grep по `sample_`/`counter`/`session`/`player`/`vehicle`/`greet`/`echo` — 0 в коде)
- Lua binder не знает HTTP/crypto/database: `source/sdk/bind/bind.hpp` включает только `sdk/lua/*`, `sdk/abi/module.hpp`, `sdk/runtime/callback.hpp` и std; grep `http|crypto|sha256|database|sqlite|mysql` по `source/sdk` — единственное совпадение, комментарий-пример в `registry.hpp:97`
- Internal layers сохранены при создании фасада (PHASE 3): `source/sdk/{abi,lua,bind,registry,runtime,resources,objects,events,logging,errors}` + `source/library/base` существуют; `sdk.hpp:12-17` явно документирует их как внутренние и сохранённые

## Рекомендации по устранению
1. Реализовать макрос `MTA_STATE` и API `mta::state` (state-обёртка над `lua_State` в слое `source/sdk/lua`), поскольку оба явно названы в чек-листе задачи как обязательные public APIs.
2. Экспортировать `MTA_STATE` и `mta::state` через umbrella header `source/mta/sdk.hpp` рядом с `MTA_FUNCTION`/`MTA_OBJECT`/`MTA_METHOD` и обновить список экспорта в документации фасада (`sdk.hpp:12-17`).
3. Устранить прямое обращение к синглтону Registry в `source/functions/info/functions_list.cpp:11,24`: заменить `mta::registry::Registry::instance().functions()` на фасадный API, предназначенный developer code.
4. Перевести `source/functions/async/timers.cpp:19,35` с `mta::async::Scheduler::instance().post_timer()`/`cancel_timer()` на предназначенный developer'у путь `mta::timer::after/every`, либо зафиксировать в задаче/фасаде, что Scheduler — допустимый для functions API, и закрыть расхождение с чек-листом документированно.
5. Убрать из `source/functions/info/version.cpp:12-13` прямое использование ABI-слоя `mta::module::info()`/`manager()` (`source/sdk/abi/module.hpp`): добавить фасадную обёртку (например, в составе `mta::Resource` или отдельного API `mta::module` в списке экспорта) и задокументировать её в `sdk.hpp`, либо заменить на существующий экспортированный API.
6. После правок перепроверить grep'ами из аудита: `MTA_STATE`/`mta::state` по `source/` (ожидается ≥ 1 совпадение) и обращения к `Registry::instance`/`Scheduler::instance`/`mta::module` в `source/functions/` (ожидается 0 либо документированное исключение).

## Статус исправления (2026-09-02)

**Реализовано.**

1. **MTA_STATE / mta::state** (несоответствие 1, рекомендации 1–2). Новый лёгкий state-слой `source/sdk/lua/state.hpp`: класс `mta::state` — borrowed view над `lua_State` для synchronous-операций (plan §18/§45: `handle()/valid()/top()/resource_name()/args<Ts...>()/push_results(...)`; VM никогда не кэшируется) — и макрос `MTA_STATE(L)` (выражение). Оба экспортированы через `source/mta/sdk.hpp` рядом с `MTA_FUNCTION`/`MTA_OBJECT`/`MTA_METHOD`; список экспорта в шапке фасада обновлён. Рабочий пример: `source/functions/state/view.cpp` (`sample_state` строится на `MTA_STATE`) + проверки в `other/tests/lua/scripts/015_facade.lua`.
2. **Registry → фасад** (несоответствие 2, рекомендация 3): оба обращения `mta::registry::Registry::instance().functions()` в `functions_list.cpp` заменены на `mta::registered_functions()` — новый inline-хелпер в `source/mta/sdk.hpp` поверх registry (read-only вид тех же `Spec`; singleton остаётся internal, plan §42). Поля, читаемые `module_functions`/`module_signature`, не изменились.
3. **Scheduler → mta::timer** (несоответствие 2, рекомендация 4): `sample_timer`/`sample_timer_cancel` переведены на developer-путь `mta::timer::every(L, delay_ms, repeat_count, fn)` — добавлена перегрузка с лимитом повторений в `source/sdk/runtime/timer.{hpp,cpp}` (семантика планировщика не тронута: tick = 1..N, `repeat_count <= 0` = forever); отмена — через per-resource `Store<HandleMap<id, Timer>>` (тот же паттерн, что в `timer_demo.cpp`), без `Scheduler::instance()`. Поведение функций сохранено (те же id, ticks 1..N, результаты cancel). Два задокументированных отличия: (а) отрицательный `delay_ms` теперь даёт Lua-ошибку `timer delay must not be negative` вместо молчаливого клампа до 1 ms — это контракт пути `mta::timer`; (б) `sample_timer_cancel` отменяет только таймеры `sample_timer` (пер-ресурсный store), а не любые таймеры модуля — как и заявлено в её описании. Попутно (та же подсистема, план §15) в `Scheduler::pump()` добавлен guard: таймер, отменённый из собственного колбэка, больше не ре-планируется — раньше `cancel()` из колбэка оставлял «зомби»-таймер (erase не находил таймер в списке, т.к. он находился в локальном снапшоте `due`).
4. **ABI-слой → фасад** (несоответствие 2, рекомендация 5): `mta::module::info()`/`manager()` в `version.cpp` заменены фасадными `mta::module_info()`/`mta::server_info()` — новые `source/sdk/native/module.{hpp,cpp}`; include `ILuaModuleManager10.h` из developer-кода удалён. Набор полей `sample_version` и fallback `?` сохранены; `netcode` теперь идёт через `std::uint64_t` (без сужения `unsigned long → float`); поля сервера по-прежнему опускаются, когда менеджер не привязан.

**Подтверждение.** Grep'и из аудита: `MTA_STATE`/`mta::state` присутствуют в `source/` (`state.hpp`, `sdk.hpp`, `view.cpp`); обращений к `Registry::instance`/`Scheduler::instance`/`mta::module::`/`ILuaModuleManager10` в `source/functions/` — 0. Локальная сборка/тесты НЕ запускались (см. «Не завершено»); проверена статическая согласованность включений и вызовов. Известная unity-коллизия имени `g_timers` (`timers.cpp` vs `timer_demo.cpp`) устранена переименованием в `g_sample_timers`.

Компилятором настоящие правки не проверялись; риски: точность соответствия `sample_version` в edge-случаях пустых строк менеджера и поведение `sample_timer_cancel` при self-cancel (теперь возвращает `true` и корректно останавливает таймер — поведение до фикса было некорректным и тестами не покрывалось).
