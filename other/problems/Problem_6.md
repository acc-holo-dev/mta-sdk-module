# Problem 6 — Автоматический контекст (module/function/resource/task) не добавляется фреймворком в log-сообщения mta::log

**Задача:** `other/tasks/Task_15.md` — Логирование: простой API mta::log и автоматический контекст сообщений
**Вердикт:** Проект не соответствует задаче (статическая проверка, 2026-09-02)
**Серьёзность:** P1 — значимые требования чек-листа выполнены лишь частично: автоматическая атрибуция контекста есть только у debug-сообщений через DebugPrintf с VM, а info/warn/error лишены механизма контекста и в ряде error-сообщений опущен доступный на месте вызова resource/task.

## Суть проблемы
Простой logging API `mta::log::{info,warn,error,debug}` с уровнями Debug<Info<Warn<Error<Off и выводом в консоль MTA (с fallback на stdout/stderr) реализован полностью, документирован и является основным путём логирования; structured logging не добавлялся, что соответствует условному «при необходимости». Контекст module/function/error в сообщениях присутствует, но вписывается вручную на местах вызова: фреймворк автоматически добавляет контекст только для debug-сообщений (через передачу VM в manager->DebugPrintf), а info/warn/error не получают module/function/resource/task автоматически. Ряд error-сообщений в scheduler.cpp и callback.cpp опускает resource/task, хотя эти данные доступны на месте вызова.

## Несоответствия

### 1. Framework автоматически добавляет контекст (module, function, resource, task, error) в log-сообщения там, где возможно
- **Статус:** PARTIAL
- **Требуется:** фреймворк должен сам добавлять module/function/resource/task/error-контекст в сообщения там, где это возможно.
- **Фактически:** автоматическая атрибуция есть только у debug-сообщений через DebugPrintf с VM; info/warn/error не имеют механизма контекста вовсе, task-контекст не добавляется нигде, а разработчик вписывает контекст в текст сообщения вручную.
- **Доказательство:** `source/sdk/logging/logging.hpp:43-117` — шаблоны info/warn/error/debug лишь стримят аргументы пользователя без какого-либо контекста; `source/sdk/logging/logging.cpp:34-76` — write_info/write_warn/write_error/write_debug не добавляют module/function/resource/task (только префикс "[WARN] " для warn); единственный автоматический путь — write_debug(lua_vm, ...) -> manager->DebugPrintf(lua_vm, ...) (logging.cpp:67-76), т.е. атрибуция ресурса работает только для debug и только когда разработчик сам передал VM (перегрузка debug без VM явно документирована как "no resource attribution", logging.hpp:103-117); диагностическое имя функции (source/sdk/lua/protect.hpp:36-40, устанавливается в source/sdk/bind/bind.hpp:579) используется только для текста Lua-ошибок (source/sdk/lua/stack.hpp:59-66), но не для логов; во всех местах вызова контекст вписывается вручную (например source/sdk/runtime/scheduler.cpp:271 "async: dropping a completion for resource '", entry.resource; source/sdk/abi/module.cpp:102 "module: loaded ...").

### 2. Log-сообщения содержат достаточно контекста для module, function, resource, task и error
- **Статус:** PARTIAL
- **Требуется:** log-сообщения должны содержать достаточно контекста для module, function, resource, task и error.
- **Фактически:** контекст module/function/error в сообщениях присутствует, но вписывается вручную: "module: loaded <name>" (module.cpp:102), "module: failed to register function '<name>'" (registry.cpp:34), "sample_task_run failed: ..." (task_demo.cpp:45), "event '<name>' failed: ..." (events.cpp:29); однако resource/task-контекст отсутствует в ряде error-сообщений, где он доступен на месте вызова, а для info/warn/error атрибуция ресурса невозможна в принципе (нет VM/контекста в сигнатуре).
- **Доказательство:** `source/sdk/runtime/scheduler.cpp:284,288` "async completion failed: <e.what()>" и :335,339 "timer callback failed: <e.what()>" — error-сообщения без ресурса/задачи, хотя entry.resource (используется в debug на :271) и timer.resource (в debug на :312) известны в той же функции; `source/sdk/runtime/callback.cpp:188` "callback stack overflow: ..." и :197 "module callback failed: ..." — resource_ известен (входит только в debug на :169-171), но отсутствует в error-сообщениях; scheduler.cpp:369 "async: task queue is full (...)" — без идентификации задачи/ресурса.

## Что уже соответствует
- Простой logging API реализован: mta::log::info/warn/error/debug — шаблоны с потоковой конкатенацией аргументов (source/sdk/logging/logging.hpp:43-117)
- Уровни логирования Debug<Info<Warn<Error<Off с set_level/get_level, по умолчанию Info (logging.hpp:26-36, logging.cpp:12,24-32)
- Вывод через модульный менеджер MTA: Printf для info, "[WARN] " Printf для warn, ErrorPrintf для error, DebugPrintf(lua_vm) для debug; fallback на stdout/stderr до привязки менеджера (logging.cpp:34-76)
- API экспортирован разработчику через <mta/sdk.hpp> (source/mta/sdk.hpp:28,49) и попадает в сборку через GLOB_RECURSE source/**/*.cpp (cmake/core/file.cmake:4-6)
- Простой API является основным путём логирования: ~30 мест вызова только через него (scheduler.cpp, callback.cpp, registry.cpp, events.cpp, module.cpp, functions/*), задокументирован в other/documents/api.md:232-247 и GUIDES.md:286-297, решение KEEP в other/documents/v2-audit.md:82
- Structured logging API не добавлен, но условие «при необходимости» не сработало: потребность в structured-форме нигде не зафиксирована, простой API из четырёх функций остаётся основным путём — соответствует формулировке чек-листа
- Обычный разработчик не обязан передавать контекстные значения: сигнатура требует только текст сообщения (guard sizeof...(args)), вызов mta::log::info("текст") валиден без какого-либо контекста (logging.hpp:43-101)
- Частичные механизмы контекста: debug(L, ...) атрибутирует ресурс через MTA DebugPrintf (logging.hpp:15, logging.cpp:67-76, api.md:242 "resource-attributed"); имя выполняющейся функции автоматически фиксируется биндером (bind.hpp:575-581) и попадает в диагностические ошибки "bad argument #N to '<name>'" (stack.hpp:59-66)

## Рекомендации по устранению
1. Добавить в logging API механизм автоматического контекста для info/warn/error: перегрузки или контекстный параметр (VM/контекстный объект), чтобы write_info/write_warn/write_error в `source/sdk/logging/logging.cpp:34-76` могли добавлять module/function/resource к префиксу сообщения по аналогии с существующим путём write_debug -> manager->DebugPrintf(lua_vm) (logging.cpp:67-76).
2. Обеспечить добавление task-контекста, который сейчас не добавляется нигде: передавать идентификацию задачи в сообщения там, где задача известна на месте вызова (например, в scheduler.cpp рядом с существующим использованием entry.resource и timer.resource).
3. Дополнить error-сообщения в `source/sdk/runtime/scheduler.cpp` доступным контекстом: строки 284,288 ("async completion failed") — добавить entry.resource, известный в той же функции; строки 335,339 ("timer callback failed") — добавить timer.resource, используемый в debug на :312; строку 369 ("async: task queue is full") — дополнить идентификацией задачи/ресурса.
4. Дополнить error-сообщения в `source/sdk/runtime/callback.cpp` ресурсом: строки 188 ("callback stack overflow") и 197 ("module callback failed") — включить resource_, который уже известен и используется в debug на :169-171.
5. Распространить использование диагностического имени функции, фиксируемого биндером (source/sdk/lua/protect.hpp:36-40, устанавливается в source/sdk/bind/bind.hpp:579), за пределы текста Lua-ошибок (source/sdk/lua/stack.hpp:59-66) — использовать его как автоматический function-контекст в log-сообщениях.
6. Сохранить свойство «обычный разработчик не обязан передавать контекстные значения» (guard sizeof...(args), logging.hpp:43-101): механизм контекста должен заполняться фреймворком там, где он доступен, не усложняя базовый вызов mta::log::info("текст").
7. После внедрения обновить документацию API (other/documents/api.md:232-247, GUIDES.md:286-297), где описан текущий простой API и частичные механизмы контекста (например, "resource-attributed" debug на api.md:242).

## Статус исправления (2026-09-02)

**Реализовано.**

1. **Автоматический контекст сообщений** (несоответствие 1, рекомендации 1, 5, 6). Thread-local diagnostic context в `source/sdk/lua/protect.hpp` расширен с одного имени функции до `DiagnosticContext {function, resource, task_id, timer_id}` + RAII-охранник `ScopedDiagnosticContext` (noexcept: строки только через move; `set_resource` глотает bad_alloc, т.к. guard создаётся в noexcept-трамплинах; контекст восстанавливается при выходе, поэтому «протухшая» атрибуция вне вызова невозможна). API `mta::log::{info,warn,error,debug}` не изменился. `source/sdk/logging/logging.cpp` добавляет к каждому сообщению префикс с тем, что известно на месте вызова: `[Base Module:функция @ ресурс]`, `[Base Module task #N @ ресурс]`, `[Base Module timer #N @ ресурс]` (module — имя модуля из ABI Info; `[WARN] ` остался первым тегом warn; при пустом контексте префикса нет). Контекст заполняет только фреймворк, developer ничего не передаёт (guard `sizeof...(args)` не тронут): trampolines биндера и `MTA_METHOD` через `protected_call_named` (имя функции + ресурс VM вызывающего; `bind.hpp` и `userdata.hpp` переведены на него), worker-поток (ресурс + task id вокруг `job.work()`), доставка completion (ресурс + task id), таймеры (ресурс + timer id), `Callback::call` (ресурс). `debug(L, ...)` не дублирует ресурс — его ставит DebugPrintf; `debug` без VM теперь получает ресурс из контекста, когда он известен.
2. **Достаточность контекста** (несоответствие 2, рекомендации 2–4). Отмеченные аудитом error-сообщения получают недостающий контекст через общий префикс, без правки их текста: «async completion failed» — ресурс + task id; «timer callback failed» — ресурс + timer id; «callback stack overflow» / «module callback failed» — ресурс (guard в `Callback::call`); «async: task queue is full» — функция + ресурс активного module-call контекста. task-контекст теперь присутствует и в worker-потоке (логи из фоновой работы), и при доставке completion — раньше task не добавлялся нигде.

**Выполненные рекомендации.** 1 (механизм контекста в logging), 2 (task-контекст), 3 и 4 (контекст в error-сообщениях scheduler/callback — через префикс), 5 (function-контекст биндера теперь идёт и в логи), 6 (разработчик по-прежнему не передаёт контекст), 7 (документация обновлена: `other/documents/api.md` — разделы Logging и Timers, `other/documents/GUIDES.md` — §9).

**Подтверждение / не завершено.** Статическая проверка: сигнатуры `write_*` и шаблонов в `logging.hpp` не менялись (все существующие вызовы `mta::log` совместимы без правок), guards расставлены вокруг всех путей диспетчеризации (scheduler worker/pump, callback), `write_debug` сохраняет оба перегрузочных пути. Локальная сборка/тесты НЕ запускались — централизованная сборка после всех параллельных агентов (на момент попытки win-mingw-сборки дерево содержало постороннюю in-flight ошибку в `sdk/objects/userdata.hpp`, вне данного скоупа). Риски: формат префикса не проверен на реальном MTA-сервере (в harness-моке Printf печатает текст как есть); имя модуля в префиксе — compile-time title из `config/module.toml` (как и в `sample_version`).
