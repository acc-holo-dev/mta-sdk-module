# Problem 4 — Native-типы не поддерживаются биндером как типизированные аргументы функций

**Задача:** `other/tasks/Task_13.md` — Native MTA types — безопасные обёртки нативных сущностей
**Вердикт:** Проект не соответствует задаче (статическая проверка, 2026-09-02)
**Серьёзность:** P1 — значимое нереализованное требование: главный интеграционный механизм native-типов (типизированные аргументы `MTA_FUNCTION` в стиле примера из задачи) не работает ни для одного native-типа, при этом безопасность уже реализованных обёрток не нарушена.

## Суть проблемы
Из пяти названных в задаче high-level типов реализован только `mta::Resource` (`source/sdk/native/resource.{hpp,cpp}`) — с живой валидацией через `GetResourceFromName` и безопасной обработкой invalid/deleted сущностей (`nullopt`/`nullptr`); отсутствие Element/Player/Vehicle/Object корректно обосновано замороженным ABI и явно задокументировано в коде и доках (`api.md`, `architecture.md`, `CHANGELOG.md`). Невыполненным остаётся требование применимости native-типов как типизированных аргументов функций в стиле `MTA_FUNCTION("get_name", [](mta::Player player){...})`: типизированный биндер не поддерживает ни один native-тип как параметр (`static_assert`), а `mta::Resource` используется только внутри тел функций. Итог: одно частичное несоответствие, вердикт NON_COMPLIANT.

## Несоответствия

### 1. Native-типы применимы как аргументы функций в стиле MTA_FUNCTION("get_name", [](mta::Player player) { return player.name(); })
- **Статус:** PARTIAL
- **Требуется:** native-типы принимаются как типизированные аргументы зарегистрированных функций (пример из задачи — лямбда с параметром `mta::Player` в `MTA_FUNCTION`).
- **Фактически:** ни один native-тип не является поддерживаемым типом параметра биндера (compile-time `static_assert`) и не поддерживается как результат (`push_one`). Native-типы применимы в функциях лишь опосредованно — внутри тела через `mta::Resource::current(L)`/`find(name)` (`resource_info.cpp`). Для несуществующих типов (Player и др.) это следствие задокументированного ограничения ABI, но условие задачи («только если соответствующий MTA API доступен и может быть представлен безопасно») покрывает набор добавляемых типов, а не способ их интеграции с биндером: для реализованного `mta::Resource` безопасная конвертация аргумента (строка-имя → `Resource::find` с валидацией) была реализуема (прецедент name-based идентичности уже есть — `mta::lua::context` в `bind.hpp:70-74`), но не сделана.
- **Доказательство:**
  - `source/sdk/bind/bind.hpp:13-24` — список поддерживаемых типов параметров не содержит ни одного native-типа;
  - `source/sdk/bind/bind.hpp:399-402` — else-ветка `pull_arg` с `static_assert(!sizeof(U), "unsupported parameter type (see lua/bind.hpp)")`, т.е. `mta::Resource` (как и Player/Element/Vehicle/Object) как параметр типизированной лямбды `MTA_FUNCTION` не компилируется;
  - `source/sdk/lua/stack.hpp:253-305` — нет перегрузки `push_one` для `mta::Resource`, т.е. native-тип нельзя и вернуть из такой функции;
  - единственное использование native-типа — внутри тел функций: `source/functions/info/resource_info.cpp:13,27` (`mta::Resource::current(L)` / `mta::Resource::find(name)`), а не как аргумент;
  - `grep 'class (Player|Element|Vehicle|Object)'` по `source/` — 0 совпадений.

## Что уже соответствует
- Реализован high-level тип `mta::Resource` — `source/sdk/native/resource.hpp:32-61` (`find(name)`, `current(L)`, `name()`, `vm()`, `alive()`) и `resource.cpp`; включён в публичный фасад `source/mta/sdk.hpp:26,44`.
- Условие «типы добавляются только если соответствующий MTA API доступен и может быть представлен безопасно» соблюдено: за замороженным ABI нет element/player/vehicle API (`other/third_party/mta-sdk/ILuaModuleManager10.h:42-78` — только `GetResourceFromName`/`GetResourceName` и служебные методы), поэтому добавлен лишь безопасно представимый Resource.
- Отсутствие `mta::Element/Player/Vehicle/Object` явно отражено в архитектуре/доках: `resource.hpp:5-13`, `other/documents/api.md:436-441` («Player/Vehicle/Element wrappers are intentionally absent»), `other/documents/architecture.md:162-164`, `CHANGELOG.md:77-83`, `other/documents/v2-phase-reports.md:356-380` (отчёт PHASE 9).
- Type wrappers валидируют underlying MTA entity: `Resource::find` проверяет существование через `manager->GetResourceFromName != nullptr` (`resource.cpp:17-22`), `vm()` выполняет живой lookup при каждом вызове и не кэширует `lua_State` (`resource.hpp:46-52`, `resource.cpp:36-44`).
- Invalid/deleted entities обрабатываются безопасно: `find()` возвращает `std::nullopt` для неизвестного/остановленного ресурса или отсутствующего менеджера (`resource.cpp:12-22`), `vm()` возвращает `nullptr` после остановки ресурса, `alive()` = `vm() != nullptr`; семплы обрабатывают `nullopt` (`resource_info.cpp:13-17, 27-35`); тест `other/tests/lua/scripts/060_features.lua:42-44` покрывает найденный/неизвестный ресурс.
- PHASE 9 «Добавить safe wrappers where possible» выполнен: safe-обёртка Resource добавлена там, где это возможно за замороженным ABI (коммит 5ef221f «feat(v2): PHASE 9 - Native MTA types: safe Resource wrapper»); ограничение задокументировано в заголовке слоя.

## Рекомендации по устранению
1. Расширить список поддерживаемых типов параметров в `source/sdk/bind/bind.hpp:13-24`: добавить `mta::Resource` как тип параметра типизированной лямбды `MTA_FUNCTION`, устранив попадание этого типа в else-ветку `pull_arg` со `static_assert` (`bind.hpp:399-402`).
2. Реализовать безопасную конвертацию аргумента для `mta::Resource` по прецеденту name-based идентичности `mta::lua::context` (`bind.hpp:70-74`): принимать строку-имя ресурса и преобразовывать её через `Resource::find` с живой валидацией; для неизвестного/остановленного ресурса определить и задокументировать безопасное поведение (ошибка регистрации/вызова либо явный сигнал «not found»).
3. Добавить перегрузку `push_one` для `mta::Resource` в `source/sdk/lua/stack.hpp:253-305`, чтобы native-тип можно было не только принимать, но и возвращать из зарегистрированных функций (например, вернуть имя ресурса или сам wrapper, если он представим в Lua безопасно).
4. Покрыть новую интеграцию тестами в стиле примера из задачи: зарегистрировать функцию вида `MTA_FUNCTION("get_name", [](mta::Resource resource){ return resource.name(); })` и расширить `other/tests/lua/scripts/060_features.lua` случаями найденного и неизвестного ресурса (обработка `nullopt`), а также сценариями invalid/deleted ресурса.
5. Обновить документацию (`other/documents/api.md`, `architecture.md`, `CHANGELOG.md`) и заголовок слоя `resource.hpp:5-13`: указать, что `mta::Resource` применим как типизированный аргумент/результат функций, и зафиксировать, что распространение механизма на Player/Element/Vehicle/Object остаётся заблокированным замороженным ABI до появления соответствующих методов в `ILuaModuleManager10.h`.

## Статус исправления (2026-09-02)

Исправлено. Верификация только статическая (read/grep, согласованность сигнатур); сборка выполняется отдельно, централизованно. Безопасность уже реализованных обёрток не нарушена (`resource.cpp` не изменялся: живой lookup через `GetResourceFromName`, без кэширования `lua_State`).

- Рек. 1 — выполнена: `mta::Resource` — поддержанный тип параметра типизированной лямбды (`MTA_FUNCTION("...", [](mta::Resource resource){...})` компилируется; ветка в `pull_arg`, `source/sdk/bind/bind.hpp`; список типов в шапке файла дополнен).
- Рек. 2 — выполнена: аргумент — строка-имя, преобразуется через `Resource::find` с живой валидацией при каждом вызове; для неизвестного/остановленного ресурса выбрано понятное сообщение об ошибке вызова: `bad argument #N to 'name' (no running resource '...')` — категория `InvalidObject`, новый хелпер `bad_argument_object` в `source/sdk/lua/stack.hpp` (сам stack.hpp от native-типов не зависит). Нестроковый аргумент → типовая ошибка `expected resource, got ...`; числа намеренно НЕ коэрцируются (имя-идентификатор, не текст) — задокументировано в `api.md`.
- Рек. 3 — выполнена с уточнением размещения: `push_one(lua_State*, const mta::Resource&)` добавлен в `source/sdk/native/resource.hpp`, а не в `stack.hpp` — native-слой стоит НИЖЕ lua-слоя в документированной иерархии (architecture.md §3), поэтому lua-слой не должен включать native-заголовок; перегрузка находится через argument-dependent lookup по типу `mta::Resource` из `push_result` (`bind.hpp`) и `push_results` (`stack.hpp`), так что доступна везде, где пушатся результаты. Wrapper представим в Lua только своим именем (стабильная идентичность; «дескриптор» за ABI не существует) — задокументировано.
- Рек. 4 — выполнена: `source/functions/native/resource_args.cpp` — `sample_resource_arg` (аналог примера из задачи: `[](mta::Resource resource){ ... }`), `sample_resource_arg_optional` (optional-параметр, nil/absent → nil), `sample_resource_return` (возврат wrapper'а). `060_features.lua` расширен: найденный ресурс, неизвестный ресурс (точная строка ошибки), строгий отказ на число, optional→nil, roundtrip возврата, метаданные `resource`/`string or nil`.
- Рек. 5 — выполнена: обновлены `api.md` (таблицы параметров/результатов, подраздел «`mta::Resource` as a typed binder argument/result»), `architecture.md` (§3.3/§3.4), `CHANGELOG.md` ([Unreleased]/Added), заголовок слоя `native/resource.hpp`. Позиция по Player/Element/Vehicle/Object сохранена: за замороженным ABI нет API — обёртки не выдумывались, механизм задокументирован как расширяемый только при появлении безопасно представимых типов.

Чем подтверждено: статическое чтение всех изменённых файлов; `Resource::find`/`vm()` не изменялись; ветки биндера аддитивны; существующие вызовы MTA_FUNCTION не затронуты. Сборка/тесты — отдельным централизованным прогоном.
